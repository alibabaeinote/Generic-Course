# حاکمیت پروژه و همکاری عامل‌ها

این سند قرارداد واحد همکاری برای توسعهٔ وب‌سایت «اردوی آنلاین مهارت‌آموزی دیزاین‌آگاهی» است. هدف آن این است که Codex، Claude Code و مالک محصول روی یک پروژه، یک معماری، یک سیستم طراحی و یک منبع حقیقت کار کنند.

## ۱. منبع حقیقت واحد

هر موضوع فقط یک مرجع اصلی دارد:

| موضوع | منبع حقیقت | قاعده |
|---|---|---|
| هدف، دامنه، نیازمندی و معیار پذیرش | [`PRD.md`](PRD.md) | تغییر دامنه بدون ثبت در PRD معتبر نیست. |
| تصمیم نهایی و استثناها | [`DECISIONS.md`](DECISIONS.md) | تصمیم نهایی با کد، تاریخ، دلیل و اثر ثبت می‌شود. |
| معماری و انتخاب فناوری | [`TECH-STACK.md`](TECH-STACK.md) | معماری تازه باید با این سند سازگار یا در آن ثبت شود. |
| روایت و محتوای محصول | [`content/`](content/) | متن جدید باید با راهنمای محتوا و منبع محتوایی مربوط هماهنگ باشد. |
| ظاهر، توکن‌ها و کامپوننت‌ها | [`design-system/style-guide.md`](design-system/style-guide.md) | مقدار رنگ، تایپ، فاصله و حالت‌ها بیرون از این سند تعریف نمی‌شود. |
| قرارداد رویدادها و شاخص‌ها | [`ANALYTICS.md`](ANALYTICS.md) | event جدید بدون به‌روزرسانی قرارداد معتبر نیست. |

README فقط نمایه و نقطهٔ ورود است و نباید نسخهٔ دوم هیچ سندی شود.

## ۲. معماری واحد

معماری مصوب فعلی، همان معماری ثبت‌شده در `TECH-STACK.md` است:

- Next.js App Router + TypeScript در زمان شروع پیاده‌سازی؛
- محتوای فایل‌محور در `content/` تا بعد از cohort اول؛
- RTL واقعی با ویژگی‌های CSS منطقی؛
- کامپوننت‌های اختصاصی و primitiveهای accessible؛
- v1 بدون دیتابیس و با CTA ثبت‌نام بیرونی؛
- لایه‌های مستقل برای analytics، payment، storage، mailer و validation از فازهای مربوط؛
- هیچ CMS، microservice، اپ موبایل یا abstraction جدیدی پیش از نیاز اثبات‌شده ساخته نمی‌شود.

اگر نیاز جدیدی با این معماری ناسازگار است، ابتدا یک تصمیم در `DECISIONS.md` ثبت و سپس `PRD.md` یا `TECH-STACK.md` را اصلاح کن؛ کد نباید پیش از آن معماری موازی بسازد.

## ۳. سیستم طراحی واحد

`docs/design-system/style-guide.md` مرجع ظاهر منتخب Graphic Blue است. `step-0.md` فقط بخش‌های معماری/نام‌گذاری/RTL/دسترسی‌پذیری را به‌صورت بایگانی نگه می‌دارد و منبع مقدارهای بصری نیست.

قواعد مهم:

- مقدار خام رنگ یا تایپ در کامپوننت جدید نوشته نشود؛ از توکن و نقش معنایی استفاده شود.
- RTL با ویژگی‌های منطقی پیاده‌سازی شود؛ فاصله‌گذاری فیزیکی و چپ/راست hardcode نشود.
- تغییر بصری بدون حذف یا تغییر معنای محتوای مصوب انجام شود.
- هر کامپوننت تعاملی حالت‌های `default`, `hover`, `active`, `focus-visible`, `disabled`, `loading`, `error`, `empty` و `success` را تا جایی که کاربرد دارد مشخص کند.

## ۴. مدل کار هم‌زمان

دو عامل می‌توانند هم‌زمان کار کنند، اما هرگز روی یک checkout مشترک ننویسند.

1. هر عامل branch/worktree مستقل داشته باشد.
2. نام branch شامل عامل و موضوع باشد، مانند `codex/<topic>` یا `claude/<topic>`.
3. پیش از شروع: `git fetch origin` و مقایسهٔ branch با شاخهٔ پایه.
4. تغییرات کوچک و موضوع‌محور commit شوند؛ commit نیمه‌کاره یا چندموضوعی ساخته نشود.
5. پیش از push: تغییرات branch پایه merge/rebase، سپس lint/typecheck/test/build اجرا شود.
6. merge به شاخهٔ اصلی فقط پس از عبور CI و بررسی تغییرات انجام شود.
7. پس از merge، عامل دیگر باید branch خود را با شاخهٔ اصلی همگام کند؛ commit قدیمی مبنای کار نیست.

### قانون فایل‌های مشترک

فایل‌هایی مثل `PRD.md`، `DECISIONS.md`، `TECH-STACK.md` و `style-guide.md` فایل‌های هماهنگی‌اند. اگر یک عامل در یکی از آن‌ها تغییر دارد، عامل دیگر در همان زمان همان فایل را ویرایش نکند. اگر تعارض رخ داد، هیچ نسخه‌ای خودکار برنده نیست؛ تصمیم ثبت‌شده و تاریخچهٔ Git مبناست.

## ۵. پروتکل تغییر

هر تغییر باید این زنجیره را طی کند:

`درخواست → بررسی منبع حقیقت → تصمیم/ثبت سند در صورت نیاز → پیاده‌سازی → اعتبارسنجی → commit → push → merge → deploy → بررسی live`

وضعیت‌ها باید دقیق گزارش شوند:

- **Draft:** فقط در working tree؛
- **Committed:** در commit محلی؛
- **Pushed:** روی remote؛
- **Merged:** در branch اصلی؛
- **Deployed:** روی سرویس انتشار؛
- **Live-verified:** با باز کردن نسخهٔ منتشرشده و بررسی رفتار واقعی تأیید شده.

هیچ‌کدام جای دیگری را ثابت نمی‌کند.

## ۶. حل تعارض و اختلاف تصمیم

- تعارض کد: بر اساس قراردادهای PRD، معماری و design system حل شود؛ نه بر اساس سلیقهٔ عامل.
- تعارض محتوا: `content-guidelines.md` و سپس `PRD.md` مرجع‌اند؛ متن تأییدنشده به محصول وارد نشود.
- تعارض معماری یا scope: اجرای کد متوقف و یک D-number جدید در `DECISIONS.md` ثبت شود.
- تعارض هم‌زمانی Git: تغییرات local عامل دیگر حفظ شود؛ هیچ `reset --hard` یا overwrite استفاده نشود.

## ۷. Definition of Done مشترک

یک کار فقط وقتی Done است که:

- منابع حقیقت مرتبط به‌روز شده باشند؛
- هیچ فایل تغییرکردهٔ ناشناخته یا تغییر خارج از scope باقی نمانده باشد؛
- تست متناسب با ریسک اجرا شده باشد؛
- وضعیت Git و commit مشخص باشد؛
- اگر انتشار درخواست شده، push، deploy و live verification جداگانه گزارش شده باشند.

## ۸. تغییر این قرارداد

تغییر این سند یک تغییر حاکمیتی است و باید در همان commit، دلیل و اثر خود را در `DECISIONS.md` ثبت کند. هیچ agent prompt، چت یا فایل موقتی نمی‌تواند این قرارداد را بی‌صدا override کند.
